# screen2litematic — план

Цель: скриншот Minecraft Java (FOV 70–110, неизвестная позиция камеры) → `.litematic` с максимально точной копией видимой постройки.

Зачем: по скрину восстановить локацию, чтобы потом искать её в мире, подбирать сид и т.п.

Рабочая машина: **Windows, Intel Arc A380 (6 ГБ VRAM)**.

## 0. Главное решение: обучение с учителем, а не RL «на случайных литематиках»

Идея «нейронка генерирует случайные литематики и получает награду» не взлетит:

- **Пространство ответов огромное.** Например, 64³ блоков × ~1000 типов. Случайный поиск с наградой почти никогда не попадёт в нужный ответ. На соревновании IGLU 2022 лучший RL-агент для строительства набрал всего F1≈0.25.
- **Награда за «похожесть рендера» ничего не говорит о скрытых блоках** (задняя стена, интерьер). При этом её легко «взломать».
- **Правильный ответ у нас уже есть бесплатно.** Мир PepeLand хранит, какой блок где стоит. Ставим камеру, делаем скрин, и разметка готова. Это прямое обучение с учителем: оно в сотни раз эффективнее.

Идея с наградами остаётся, но на своём месте (этап 5). Это проверка «отрендерь свой ответ и сравни со скрином», которая доводит результат. Позже на ней можно сделать RL-дообучение на реальных скринах без разметки.

Ближайшая работа: **World2Minecraft / MinecraftOcc** (arXiv 2604.27578, апр. 2026). 100k скринов Minecraft с позами камеры и воксельной разметкой; там сравнивали MonoScene, Symphonies, ISO и NDC-Scene. Значит, подход рабочий, но точность у существующих моделей пока средняя (IoU ~40%). Готового «скрин → схематика» нет.

## 1. Архитектура (пайплайн)

```
скрин ──► [A] камера: FOV + поворот + привязка к сетке блоков
     └──► [B] 2.5D-сеть: на каждый пиксель глубина, грань (±X/±Y/±Z), тип блока, состояние
              │
              ▼
          [C] подъём в 3D: пиксели → точки на гранях → координаты блоков (видимая часть почти точно)
              │
              ▼
          [D] 3D-достройка: sparse 3D U-Net достраивает скрытое и исправляет ошибки
              │
              ▼
          [E] render-and-compare: рендерим ответ той же камерой, сравниваем, правим сомнительные блоки
              │
              ▼
          [F] экспорт .litematic
```

Почему так: в Minecraft всё выровнено по сетке, и 1 блок = 1 метр. Поэтому сложная задача «восстановить 3D» сводится к классификации: какой блок и в какой клетке.

### [A] Камера

- **Свойства камеры.** FOV в настройках Minecraft **вертикальный**, по умолчанию 70, максимум 110. Дисторсии нет, центр кадра — главная точка, крен ≈ 0. Реальный FOV меняют спринт, полёт и зелья (×1.1–1.15), поэтому его надо **оценивать**, а не брать из настроек.
- **Оценка.**
  1. Сеть даёт грубую оценку FOV и наклона: голова на backbone или готовые MoGe-2 / GeoCalib.
  2. Точный FOV и поворот считаются по точкам схода рёбер блоков (мир «манхэттенский»).
  3. Решётка блоков даёт масштаб и сдвиг: по шагу рёбер на плоскости находится глубина, а смещение вычисляется с точностью до целого блока.
- **Итог:** матрица K + поворот R, выровненный по осям мира. Поворот на 90° по yaw для схематики не важен.

### [B] 2.5D-сеть (основная)

- **Backbone:** DINOv2 (Apache) или дообучаем MoGe-2 (MIT), который уже умеет глубину, нормали и FOV.
- **Выходы на каждый пиксель:**
  - глубина (можно классифицировать по пересечениям луча с сеткой);
  - направление грани (6 классов);
  - **тип блока**;
  - **состояние блока**: facing / half / shape / axis для ступенек, плит, логов, дверей.
- Выходы **факторизованные** (материал / форма / ориентация), а не один softmax на 5000 классов.

### [C] Подъём в 3D

- Каждая точка на грани даёт координату блока: `floor(точка − нормаль·ε)`.
- Голосование пикселей внутри клетки определяет итоговый тип блока.
- Этот шаг — чистая геометрия, без обучения.

### [D] 3D-достройка

- **Модель:** sparse 3D U-Net в стиле MonoScene / ISO на сетке ~64³ вокруг постройки.
- **Вход:** видимые блоки с уверенностями и признаки из 2D.
- **Выход:** занятость, материал и ориентация для всех клеток.
- **Предобучение «знания о постройках»** (симметрия, стены, крыши) через masked voxel modeling на корпусах схематик: сами миры PepeLand, 3D-Craft, HF Minecraft-Schematics.

### [E] Render-and-compare (здесь живут «награды»)

1. Рендерим предсказание той же камерой: свой рендерер на moderngl или deepslate. Получаем карты ID блоков и нормалей.
2. Сравниваем со скрином. Сравнение идёт по выходам сети [B] и признакам, а не по сырым пикселям.
3. Жадно или beam-поиском перебираем сомнительные клетки и оставляем вариант с лучшим совпадением.
4. Позже (опционально): GRPO/DPO-дообучение на реальных скринах без разметки, с этой метрикой как наградой.

### [F] Экспорт

- Библиотека: `litemapy` (GPL-3) или `nucleation` (MIT, Rust, быстрее; умеет ещё .schem и чтение миров).
- CLI: `screen2litematic shot.png -o house.litematic`.

## 2. Данные — самое важное

### 2.1 Источники

| Что | Зачем |
|---|---|
| **PepeLand S8–S10**: официальные загрузки `pepeland.net/about/seasons/N/worlds`; S10 = 1.21.8, миры построек ~3 + 6.5 ГБ в архиве | основной трейн |
| Hermitcraft (официальные загрузки миров) | разнообразие стилей |
| HF Minecraft-Schematics, 3D-Craft | предобучение 3D-приора [D] |
| **Твои дома разной сложности** | **тестовый набор** (не трейн!): честная проверка на постройках, которых сеть не видела |

⚠️ Лицензии на миры PepeLand нет; по правилам сайта контент принадлежит авторам. Для личного обучения риск низкий. Чтобы публиковать датасет или модель, нужно спросить админов.

### 2.2 Генератор датасета (data engine)

1. **Индексатор мира (Python + numpy).**
   - Читает region-файлы Anvil и раскладывает блоки в массивы.
   - Находит постройки: кластеры «неприродных» блоков и их bbox.
   - Сэмплирует позы камеры вокруг построек: дистанция 3–80 блоков, взгляд на постройку, FOV ~ U(70, 110).
2. **Fabric-мод захвата (MC 1.21.8, Java 21).** Запускается на Windows через Fabric client gametest: Xvfb нет, клиент работает в обычном окне. Параллельно 1–2 инстанса, больше A380 не потянет. Для каждой позы:
   1. spectator + телепорт на позу;
   2. ждём прогрузку чанков;
   3. скрываем HUD, отключаем покачивание камеры, FOV Effects = 0;
   4. делаем скриншот;
   5. логируем pos / yaw / pitch, фактический FOV (mixin на `GameRenderer.getFov`) и разрешение;
   6. **эталон:** блок, состояние, грань и глубина на каждый пиксель. Сохраняем в `.npz`. Raycast `world.raycast` на каждый пиксель — ~2 млн лучей на кадр при 1080p, слишком медленно. Варианты:
      - ID-буфер и буфер глубины через свой шейдер в моде (быстро, основной вариант);
      - raycast на сетке с шагом 4 px + достройка по граням (проще, для старта).
3. **Рандомизация** против разрыва «трейн ≠ реальные скрины» (domain gap):
   - время суток, погода, мягкое освещение, Fast/Fancy, дальность прорисовки;
   - FOV ~ U(70, 110): цель только такие скрины, FOV < 70 (подзорная труба, лук) не поддерживаем;
   - ресурспаки: **v1 — только ванильный**; потом популярные паки (Bare Bones и т.п.) и пак PepeLand;
   - шейдеры — не планируются;
   - иногда видимый HUD и рука;
   - JPEG-сжатие и ресайз.
4. **Разметка сцены.**
   - Видимые блоки берём из raycast.
   - Полный объём постройки в кропе 64³ берём из индекса мира.
5. **Объём.** MVP — ~20–50k кадров, потом 200k+. Ожидаем ~1–3 кадра/с на инстанс (оценка).

Дешёвый вариант для быстрого старта: свой рендерер на moderngl по ванильным текстурам (сотни кадров/с, идеальные ID- и depth-буферы). На нём предобучение, потом дообучение на кадрах из настоящего клиента.

## 3. Этапы (вехи)

| # | Веха | Готово, когда |
|---|---|---|
| M0 | Окружение: Python/PyTorch, Fabric 1.21.8, скачан PepeLand S10, запись/чтение .litematic | тестовая схематика открывается в Litematica |
| M1 | Индексатор мира + Fabric-мод захвата | 1000 кадров с pose + raycast-разметкой, визуальная проверка совпадения |
| M2 | **MVP end-to-end:** только полные кубы, топ-50 блоков, FOV известен | скрин → .litematic, видимые блоки IoU > 0.7 на валидации |
| M3 | Оценка камеры [A] при FOV 70–110 | ошибка FOV < 2°, поворота < 1° |
| M4 | Все блоки PepeLand + состояния (ступеньки, плиты, заборы, двери) | точность типа блока > 85% на видимых |

| M7 (опц.) | 2–3 скрина одной постройки: по каждому своя гипотеза, потом их совмещение в одну схематику | сильно лучше достраивается скрытое |

## 4. Метрики

- **IoU видимых блоков** — главная: «что видно, то скопировано».
- Точность типа блока и состояния (по видимым).
- IoU полного объёма (со скрытым) — вторично.
- Тест: твои дома, 3 уровня сложности, по 10–20 скринов каждый, с разных углов и FOV.

## 5. Стек и железо

- **ML:** Python 3.11, PyTorch, numpy, litemapy/nucleation.
- **Мод:** Java 21 + Fabric (Loom).
- **Рендерер:** moderngl или deepslate.
- **ОС:** Windows. Пути, скрипты и запуск — под Windows (PowerShell), без Xvfb и Linux-only инструментов.
- **GPU:** Intel Arc A380, 6 ГБ VRAM. PyTorch через бэкенд XPU (`torch.xpu`), не CUDA.
  - MVP (M2): маленький backbone (DINOv2-S / MoGe-2 small), пониженное разрешение, малый батч, mixed precision.
  - M5+ (3D U-Net, предобучение на схематиках): скорее всего нужна облачная GPU.
  - Захват данных идёт на той же карте → захват и обучение не запускать одновременно.
- Не использовать: Amulet (стал платным), Chunky (медленно), MineRL/MineDojo (старые версии MC).

## 6. Риски

- **Мелкие далёкие блоки.** На 1080p блок в 60 м — пара пикселей. Ограничиваем дистанцию и работаем в нативном разрешении (тайлами).
- **Прозрачное и сложное:** стекло, листва, вода, сущности, рамки, баннеры. На старте игнорируем или упрощаем.
- **Скрытое не восстановить точно** с одного скрина, только угадать. Решение — режим нескольких скринов (M7).
- **Чужие ресурспаки игрока.** Лечится рандомизацией при генерации. Шейдеры не поддерживаем.
- **Слабая GPU (6 ГБ).** Ограничивает размер модели и скорость захвата; тяжёлые этапы — в облако.
- **Права на миры PepeLand** — см. 2.1.

## 7. Решения и открытые вопросы

Решено:
1. Видеокарта — Intel Arc A380 (6 ГБ), Windows.
2. Вход — 1 скрин. Позже 2–3 скрина (M7), режим ещё не выбран.
3. v1 — ванильные текстуры; позже популярные ресурспаки (Bare Bones и т.п.); без шейдеров.
4. FOV — только 70–110.

Открыто:
1. Версия MC — ок 1.21.8 (как PepeLand S10)?
2. Что важнее на выходе: точная оболочка (видимое) или «правдоподобный» интерьер?
3. Есть ли доступ к облачной GPU для M5+?
